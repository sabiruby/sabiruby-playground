# 2026-09-21 — ステッパが `Vm::next_line` を呼ぶ（`current_line` の改名に追随）

SabiRuby の `Vm::current_line` が `Vm::next_line` に改名された（著者の許可、2026-09-21）。
振る舞いは 1 つも変わっていない — 返るのは今までどおり `line_of(ci.pc)`、
**次に実行する命令の行**である。名前が「呼び出し元の行」と読めるのが問題だった、という改名で、
ステッパにとっては最初から `line_of(pc)` の方が正しい答えだったので、
**この repo がやることは呼び名を替えるだけ**。

改名の理由と、古い名前を消す条件は sabiruby 側にある:
[`docs/plans/serde-declare-lines-plan.md` §4](https://github.com/sabiruby/sabiruby/blob/main/docs/plans/serde-declare-lines-plan.md)、
[`docs/worklog/2026-09-21-serde-lines.md` §7](https://github.com/sabiruby/sabiruby/blob/main/docs/worklog/2026-09-21-serde-lines.md)。

## 何を替えたか

`wasm/src/lib.rs` の `sabi_step_until` の 2 行（`line0` を取るところと、1 命令進めたあとの
`line`）。ほかに `current_line` を呼んでいる所は無い。

`docs/plans/visualizer-plan.md` の 2 か所（84 行・167 行）は**そのまま**にした。
2026-09-12 に済んだ計画書で、その時点の記録だからである（sabiruby 側も同じ扱いで、
過去の worklog と済んだ計画書の本文は書き替えていない）。

## いつ main に入れてよいか

**まだ入れられない。** このブランチは 3 つの repo が 1 本の線で繋がっている所に触っている:

```
rubevy_games/.github/workflows/pages.yml
   └─ playground の main を、games の Cargo.lock が固定する sabiruby の rev に対して建てる
        （今は 50cae754。lock の git+https://github.com/sabiruby/sabiruby#… を読む）

sabiruby-playground/.github/workflows/pages.yml
   └─ SABIRUBY_REF（今は 7be7b86 = v0.5.2）を checkout して建てる

sabiruby-playground/wasm/Cargo.toml
   └─ sabiruby = { path = "../../sabiruby" }   ← 上の 2 つがそれぞれ何を隣に置くかで決まる
```

`next_line` は **`574aeff`（sabiruby の main）より後**にしか無いので、`7be7b86` でも
`50cae754` でも建たない。入れる順番:

1. **sabiruby の `next-line` を main に入れて push。** `next_line` が生え、
   `current_line` は `#[deprecated]` の別名として残るので、どちらの名前も通る状態になる。
2. **rubevy_games の `Cargo.lock` の sabiruby の rev を 1 の commit まで上げて push。**
   これで games の Pages は、`next_line` のある sabiruby に対して playground を建てるようになる
   （まだ playground の main は `current_line` を呼んでいるが、別名があるので通る）。
3. **このブランチを main に入れる。その commit で `pages.yml` の `SABIRUBY_REF` も
   1 の commit に上げる**（今の `7be7b86` のままだと、この repo 自身の Pages が
   `no method named next_line` で落ちる）。ここは 2 と入れ替えてもよいが、
   **1 より先には来られない。**
4. sabiruby 側で `current_line` の別名を消す（2 と 3 の CI が緑になってから、
   0.6.0 か著者の決める版で）。

`SABIRUBY_REF` をこのブランチで先に書き替えなかったのは、**1 の commit の sha がまだ
無いから**である。数を当てずっぽうで書くより、入れるときに書く方の手順に残した。

## 確かめたこと

sabiruby の作業木が main（`next_line` がまだ無い）を指しているので、`../../sabiruby` が
**`next-line` のブランチに解決する形に木を並べて**建てた: スクラッチパッドに
`pg/sabiruby` → `sabiruby-wt-next-line` の symlink と、`pg/sabiruby-playground`（この木のコピー）
を置き、`pg/sabiruby-playground/wasm` から見た `../../sabiruby` が
`sabiruby-wt-next-line` に解決することを `readlink -f` で確かめてから回した。
どちらの repo にも書いていない（`[patch]` もコミットもしていない）。

```
$ cargo check（wasm32-wasip1、wasi-sdk 34）     Finished、警告 0
$ tools/build.sh                                 Finished（wasm-opt がこの機械に無いので
                                                  最適化なしの 2,748,907 バイトをコピー）
$ node test/fixtures.mjs                         18/18 fixtures match the reference output
$ node test/api.mjs                              26/26 checks
$ node test/browser.mjs（headless Chromium）     all passed; page ready in 354 ms
```

`test/api.mjs` の `stepUntil(STEP_OVER) moves to the next line, STEP_INSTRUCTION one
instruction` と `STEP_OVER runs a call without stopping inside it, STEP_INTO stops in the
callee`、`test/browser.mjs` の `step over moves the current instruction` と
`stepping into mrblib says so…` が、**触った 2 行そのものを通る**確認である。

symlink を sabiruby の main（`574aeff`）に向け替えると、狙いどおり建たない:

```
error[E0599]: no method named `next_line` found for mutable reference `&mut Vm`
   --> src/lib.rs:316:35
   --> src/lib.rs:324:27
```

これが「順番が後」の理由そのもので、同時に、上の緑が**本当に `next-line` の sabiruby を
見て出たもの**である証拠でもある。
